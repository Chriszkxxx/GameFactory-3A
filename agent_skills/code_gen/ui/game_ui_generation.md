# Game UI Generation

Generate the engine-native UI for one task inside the prepared workspace.

## Inputs

Read before editing:

- the prepared UI packet, requirement, acceptance criteria, design document,
  general requirement, screens, viewports, constraints, and forbidden UI;
- the Pipeline-owned canonical Engine identifier;
- the existing read-only Engine Context directory;
- every required Mechanic and UI Example path;
- the Pipeline-validated Browser Play execution handoff;
- the finalized Mechanic artifact, contract, public runtime-adapter paths, and
  declared UI bindings;
- every supplied reference image;
- this Skill.

The Pipeline owns Engine identity, validation, Examples, write boundaries, and
finalization. Discover API documents inside the supplied Context directory.
Do not change the Engine or use an API or Example from another Engine.

## Delivery Ownership

The complete playable flow has two stages with different owners:

```text
1. engine_native - generated by this Agent
2. browser_play  - generated by this Agent against framework serving
```

Generate both stages in order. Do not generate Browser backend source.

### Engine Native

Generate the real gameplay HUD, widgets, menus, focus handling, layout,
feedback, resources, and native tests under `generated_ui/`.

1. Discover and read the Engine API in the Engine Context directory.
2. Read the finalized Mechanic contract and only its declared public paths.
3. Inspect every required Mechanic and UI Example.
4. Query state, subscribe to events, and invoke commands only through the
   public Mechanic runtime adapter.
5. Generate a binding manifest and mocked Mechanic fixture for native UI
   tests.

Never cast to concrete gameplay classes, dereference producer-side contract
metadata, invent bindings, copy the Mechanic contract, or reimplement rules.

### Browser Play

Generate Browser Play source and tests under:

```text
generated_ui/browser_play/
```

Use the Browser Serving API, registered backend capabilities, and
repository-owned player frontend as a read-only reference. Generate the
task-owned Web layout, interaction, stream presentation, session controls, and
generic input behavior. The streamed Engine frame already contains the
engine-native gameplay UI.

The generated page must recover a supplied Browser Serving session or create a
generic session when none is supplied. It must consume the returned
`pixel_streaming_url`, preserve native Pixel Streaming keyboard/mouse input,
and render truthful booting, ready, and error states. Do not require an
undocumented external page to create the first session.

The Browser Play output must also contain:

- `browser_play_manifest.json` using
  `aaagameforge.browser_play_manifest.v1`;
- a thin task-owned launch script referenced by that manifest.

The launch script may set the documented Browser Serving environment variables
and invoke `python -m engine_adapters.browser_serving`. This is the only allowed
process-lifecycle exception. It must not implement, copy, or import a concrete
backend directly.

Do not reproduce gameplay HUD, consume Mechanic bindings, implement stream
transport, add Engine-specific frontend branches, or generate/modify an
`EngineBackend`.

## Visual Authority

Apply inputs in this order:

1. Mechanic contract for available native bindings.
2. UI requirement, acceptance criteria, screens, constraints, and forbidden
   UI for behavior.
3. Reference images for composition, hierarchy, density, spacing, color,
   typography, and style.
4. Design and general requirements for product intent and consistency.
5. Engine Examples for implementation structure.

Inspect every reference image. Preserve higher-priority constraints when a
reference conflicts, and report the deviation.

## Required Manifests

Generate:

- `generated_ui/ui_binding_manifest.json`;
- `generated_ui/Tests/fixtures/mechanic_contract_fixture.json`;
- `generated_ui/screenshot_plan.json`;
- `generated_ui/context_used.json`;

`context_used.json` uses schema `aaagameforge.context_used.v1` and records:

- the discovered Engine API for `engine_native`;
- the discovered Browser Serving API for `browser_play`;
- every required Mechanic and UI Example.

Use repository-owned paths and record no extra or cross-Engine context.

## Tests

- Native tests use the mocked Mechanic fixture for binding, state, layout,
  interaction, and screen coverage.
- Browser frontend tests use Browser Serving fixtures and never consume the
  Mechanic fixture.
- Tests must fail when required behavior is absent; avoid empty assertions and
  unconditional success.

## Boundaries

- Write only inside the prepared workspace.
- Keep all task-owned output under `generated_ui/`.
- Treat packet inputs, Context, Examples, Mechanic artifacts, reference images,
  Skills, and Prompts as read-only.
- Do not inspect, compare against, copy, or adapt generated code or artifacts
  from other tasks or games under `test_data/outputs/` (or any relocated output
  root). The only implementation examples allowed are the Engine-validated
  Mechanic and UI Examples explicitly provided by the prepared packet under the
  selected Engine's registered Example roots, plus the repository-owned Browser
  Play frontend reference declared by the handoff. The current task workspace
  and finalized Mechanic artifact are task inputs, not implementation examples.
- Do not modify Pipeline metadata, framework backend source, or Mechanic
  source.
- Do not generate `generated_adapters/`, backend factories, stream transport,
  or Engine input injection. A manifest-declared thin launcher that invokes the
  public Browser Serving entry point is allowed.
- Keep Browser Play output under `generated_ui/browser_play/`; treat the
  repository-owned Browser Serving frontend as read-only.
- Do not create replacement contracts, fallback state stores, runtime mocks,
  or empty providers.
- Do not invoke execution/evaluation-only APIs, launch Engines, capture or
  fabricate screenshots, or declare build/test/benchmark success.

## Completion

Report changed files, covered screens and criteria, consumed Mechanic bindings,
reference-image deviations, native/frontend test coverage, and unresolved
risks. Rendering and authoritative execution belong to the Pipeline and
execution layers.

## Repair

Preserve the canonical Engine, Context/Example provenance, Mechanic contract
version, public runtime-adapter-only access, empty Browser Mechanic bindings,
registered backend dependency, Browser frontend separation, and existing
failure evidence. Apply the smallest coherent UI-owned repair without
weakening tests or changing gameplay.
